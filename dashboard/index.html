Delivery Scam Watch

Fake "your package is on hold" texts were the most reported text scam in the US last year. This monitor reads new website certificates and new domain registrations, spots names that impersonate delivery companies, mines the scam texts themselves, and hands analysts a short list before the public blocklists catch up.

Data mining · template campaigns found by code

Campaigns the code found

Scam kits stamp out names from one template: same brand, same ending, random letters in between. The code reduces every name to its template (fedex-vipbtb[.]shop → fedex-*[.]shop), groups names that share one, and adds who registered them and when (registry RDAP). No list of patterns is typed in by hand.

Scam domains die fast

Most blocklisted delivery-scam domains we looked up no longer exist (registry record checked, then confirmed with DNS: the name no longer resolves). By the time a domain reaches a blocklist, the campaign has often moved on, so the useful moment to act is when the domain is registered or gets its certificate.

The subdomain trick dominates

Most real scam names put the brand in front of an unrelated domain, like usps.com-trackdqf[.]top: on a phone screen, only the first part shows.

Analyst time, before and after

Hours a month to check every new brand-keyword domain, against checking only what the rule and model flag (five minutes per domain, an assumption).

Why it matters

Reported US losses to text-message scams in 2024; fake package delivery was the most reported type (FTC, April 2025). The FTC does not split losses by scam type, so this monitor reports operational numbers rather than a dollar figure.

What the scam texts say

Domains are only half the picture: the text message is what reaches the customer. FedEx-grounded triage · carrier specs, carrier DNS, check digits

What an analyst would see for each message

Every message is turned into one record: its links checked against the domains each carrier really owns (read from the carriers' own DNS), any tracking number checked against the carrier's real format and check digit, the lure, and a score made of named reasons. The rules come from public carrier facts: FedEx's Track API specification, the carriers' DNS records, and published tracking-number formats.

Tests behind the headlines

Ranges are 95% Wilson intervals: where the true share probably lies, given how many items it rests on. Differences between groups use a chi-square test (Fisher's exact test for small 2×2 tables); the p-value is the chance of a difference this large if the groups really had the same mix, and Cramér's V says how big the difference is (0 none, 1 complete).

Does synthetic data help when real labels are scarce?

Real confirmed scams are expensive to label, so fraud teams often lean on synthetic data. I trained the detector on a few real labels, with and without synthetic examples, and measured recall at 95% precision on real domains it had never seen. Generator B learns templates only from the same few real labels; a classifier can barely tell its output from real data (AUC ), while it spots our assumption-based generator A easily (AUC ).

real labels onlyreal + generator Areal + generator B

Read it this way: with 25 real labels, a real-only model reaches 0% recall at that precision; adding assumption-based data lifts it to 87%. From about 200 labels, real data alone is best, and generator A's wrong assumptions start to cost recall.

How good is the detector, honestly?

  • In the lab: PR-AUC with folds grouped by registered domain. This is optimistic: the legitimate examples are popular websites, which are easy to tell from scams.
  • On a brand it never saw: trained on three brands and tested on the fourth, PR-AUC ranges from . UPS is hardest, because "ups" also appears in many innocent names.
  • On the live stream: a name-only review of everything flagged found . Honest reading: the model's cut-off, set for 95% precision on lab data, keeps every name the rule passes, so the rule and a cloud-infrastructure filter do the cutting and the model score only orders the queue. Lab negatives are popular websites, too easy to teach it the hard cases; reviewed stream names are the training data it needs next.
  • Noise found and fixed: certificate logs also carry company-internal cloud host names (AWS test hosts, Snowflake endpoints) whose random strings start with "dhl". such names are now filtered out and counted separately.

Python, PostgreSQL, scikit-learn, SciPy. Tested, including a test that fails if the frozen generator A changes. A suspected scam site is never visited: everything here comes from names, certificates, registry and DNS records, and reported texts.

Limits, and how it scales

  • The certificate log is sampled (one Google log, a few thousand certificates an hour), and the WhoisDS free list is a partial daily sample.
  • The text data is mostly 2022–23 (the published dataset); the live feed adds the newest reports, but only a handful pose as a delivery so far, so the 2026 picture is thin.
  • "Likely scam" labels on new domains come from a name-only review and are not yet confirmed; confirmation comes when the domains reach a blocklist, which also measures the warning time.
  • With free accounts: urlscan.io (page screenshots and hosting), Google Safe Browsing and VirusTotal (outside confirmation), ICANN zone files (every new registration, not a sample), and a Reddit app (fresher scam texts).
